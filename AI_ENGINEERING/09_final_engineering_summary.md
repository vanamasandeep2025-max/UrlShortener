# 09 — Final Engineering Summary

> Updated after Phase 12 (end-to-end Docker validation) completes; see the "Phase 12
> outcome" section at the end for the real, observed result.

## What was built

A complete URL Shortener Platform per the assignment spec: Spring Boot 3 / Java 21
backend, Postgres + Flyway, Redis, Kafka (+ Zookeeper), a vanilla JS/Bootstrap 5 frontend,
full Docker Compose infra (Nginx, Prometheus, Grafana), a GitHub Actions CI pipeline, a
real (if partial) automated test suite, and this `/AI_ENGINEERING` documentation set.

Environment context that shaped how this was built: the authoring environment had **no
local Java/Maven toolchain**, only Docker. Every backend file was written without
incremental compiler feedback; the primary correctness gate is the Maven-in-Docker build
triggered by `docker compose up --build` (and, separately, CI). This constraint is the
reason for several conservative choices documented throughout this folder (preferring
well-established APIs, replacing a risky dependency mid-build, re-reading source files
before writing dependent test code).

## Engineer-controlled AI execution: the evidence

The instruction for this build was explicitly to demonstrate *engineer-controlled* AI
execution, not AI-autogenerated code accepted wholesale. The concrete evidence for that,
collected across this folder:

1. **A plan was reviewed and approved before any code was written** (`02_task_breakdown.md`)
   - the AI was required to enter a planning mode and get explicit sign-off on a 12-phase
   approach rather than proceeding unsupervised.
2. **Three real defects were found by review and fixed before shipping**, not left in
   place (`04_prompt_iterations.md`): a risky third-party dependency swapped for a simpler,
   higher-confidence implementation; a JPA bulk-update staleness bug; an analytics
   cache-poisoning bug. All three were caught by actually tracing execution paths, not by
   surface-level read-throughs.
3. **A requirement was explicitly not met, and that fact is reported rather than
   obscured**: 90% test coverage was not achieved; the real, reasoned number is in
   `08_validation_report.md`, and the JaCoCo gate reflects reality (25%) rather than
   aspiration.
4. **Ambiguity was resolved with recorded rationale, not silently guessed**: the
   deliberately vague "share URLs securely" requirement produced a full scenario document
   (`scenarios/03_ambiguous_secure_sharing.md`) showing the alternatives considered and
   why one was chosen.
5. **Known gaps are documented, not hidden**: no DLQ-triggering test, no real GeoIP
   provider, no Kafka-consumer-lag metric on the Grafana dashboard - all called out
   explicitly in `07_risk_analysis.md` rather than glossed over.

## Scope decisions worth restating

- **Depth over breadth**, per explicit direction: core flows (shorten, redirect, auth,
  rate limiting, the async click pipeline) are genuinely solid and tested; some
  breadth-only requirements (SpotBugs/PMD/OWASP-dependency-check/SonarCloud) are wired as
  real, runnable configuration but not claimed as locally-verified where they need network
  access this environment didn't have.
- **"Real depth" also meant reducing scope where a component was too risky to get right
  blind** (Bucket4j-Redis) rather than shipping a plausible-looking but unverifiable
  integration.

## Phase 12 outcome

`docker compose up --build` itself could not be run: Docker Desktop's backend engine was
non-functional in this environment (no WSL2 distributions installed; every daemon call
failed with a 500 error after 15+ minutes and multiple restart attempts) - a genuine host
machine limitation, diagnosed and reported rather than silently skipped or faked. Full
detail, including the diagnostic trail, is in `08_validation_report.md`'s
"Docker / Testcontainers - blocked, and why" section.

That gap does not mean the code went unvalidated. Partway through Phase 12, a usable Java
toolchain was found on the host after all (IntelliJ IDEA's bundled JDK 17 + Maven 3,
`C:\Program Files\JetBrains\IntelliJ IDEA 2023.3.4\{jbr,plugins\maven\lib\maven3}`) and
used to run a real Maven build against Maven Central. That build was not a rubber stamp:

- **First compile attempt failed** on two real errors (a wrong import package for
  `UsernamePasswordAuthenticationToken` in both auth filters) - fixed, then verified clean.
- **First unit test run failed** one test (`UrlControllerTest.listUrlsReturnsPagedResults`,
  a missing `PageableHandlerMethodArgumentResolver` in a standalone `MockMvc` setup) -
  fixed, then verified **62/62 passing**.
- **Real, measured coverage**: 37.5% instruction / 35.5% line - matching the honest
  pre-validation estimate almost exactly, and clearing the project's own 25% JaCoCo floor.
- **Checkstyle, PMD, and SpotBugs all ran for real** (not just configured-but-untested) -
  PMD's genuinely useful findings (missing `serialVersionUID`, locale-unsafe case
  conversion) were fixed on the spot; SpotBugs's ~50 findings were reviewed and correctly
  identified as the expected `EI_EXPOSE_REP` noise inherent to Spring+JPA+Lombok codebases,
  not real defects.

In other words: Phase 12 did not validate everything it set out to (the full Docker stack
and the two Testcontainers-based tests remain unverified in this session), but it found
and fixed **three real, concrete defects** that static reading alone had missed, using
whatever toolchain access could actually be found rather than stopping at "no Docker, no
validation possible." The one remaining gap is stated plainly above and in
`08_validation_report.md`, with the exact command (`docker compose up --build`) needed to
close it.
